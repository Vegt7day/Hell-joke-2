# 开关与机关链接系统（设计说明）

本文档说明**开关**与**门**的链接方式与扩展思路。

**工程现状（已实现）**：`MechanismLinkBus`（Autoload，`res://system/globals/mechanism_link_bus.gd`）为中央总线，末次写入策略；`开关.gd` 在发信号同时 `publish_channel_state`；门场景内子节点 `SwitchChannelListener`（`res://system/mechanisms/switch_channel_listener.gd`）订阅总线并调用父节点 `apply_switch_bus_state`；`Game.change_scene` 在换场**最开头**调用 `MechanismLinkBus.clear_last_states()`，关卡 `world.gd` / `world_2.gd` 在 `_ready` 开头再次清空作为兜底。监听器对总线**首次同步**使用 `call_deferred`，避免早于父节点 `@onready`；首次同步调用 `apply_switch_bus_state(..., false)` 仅改帧与碰撞、**不播开门/关门动画**；运行时总线事件仍用 `play_anim == true` 播动画。

下文仍保留「原有问题与迁移思路」供查阅其它机关类型时对照。

---

## 1. 当前实现概览

### 1.1 开关（`system/可交互物/开关.gd`）

- 节点类型：`StaticBody2D`（场景 `开关.tscn`）。
- **信号**：`switch_state_changed(color: String, switch_state: String)`  
  - `color`：与导出变量 `initial_color` 一致的中文颜色名（如 `"红"`）。  
  - `switch_state`：`"开"` 或 `"关"`（与开关 `is_on` 同步）。
- **触发**：实现 `take_damage(damage_amount, attacker)`，在伤害达到 `damage_threshold` 后内部 `_trigger_switch()`，动画结束后 `_emit_state_change()` 发信号。
- **颜色表现**：`ColorRect` 用 `match current_color` 映射到 `Color`（与门侧逻辑重复一份字符串表）。

### 1.2 门（`门.gd`，场景 `system/可交互物/门.tscn`）

- 节点类型：`StaticBody2D`。
- **导出**：`initial_color`（中文）、`is_open`（初始开/关）。
- **逻辑入口**：
  - `_on_switch_state_changed(color, state_str)`：若 `color == current_color` 且目标开/关与 `is_open` 不同，则播动画并更新碰撞。
  - `_on_开关_switch_state_changed(...)`：编辑器从名为「开关」的节点连信号时生成的槽函数；关门时先 `push_players_out()`，再转调 `_on_switch_state_changed`。
- **颜色过滤**：门只响应**与自己颜色字符串相同**的信号参数，因此天然具备「同色才联动」的语义，但依赖**谁把信号连到门上**。

### 1.3 场景中的连接方式（以 `system/levels/world.tscn` 为例）

在关卡场景里，通过 **编辑器信号连接**，把**同一个**「开关」节点的 `switch_state_changed` 连到**多个**门实例的 `_on_开关_switch_state_changed`：

```text
[connection signal="switch_state_changed" from="开关" to="door" ...]
[connection signal="switch_state_changed" from="开关" to="door/door2" ...]
...（共 4 条）
```

含义：该关卡里一个开关翻转时，**四个门节点都会收到回调**；是否动作仍由门脚本里的**颜色比较**决定。

---

## 2. 当前方式的问题（为何对「全局」不够友好）

| 问题 | 说明 |
|------|------|
| **连接与关卡强绑定** | 每加一扇门或多一个开关，往往要在 `.tscn` 里增删 `connection`，关卡多了难以维护。 |
| **回调名依赖节点名** | `_on_开关_switch_state_changed` 与节点名「开关」绑定；改名或复制关卡时易断连或需批量改方法名。 |
| **多开关、多颜色扩展成本高** | 同色多开关、不同颜色多路并存时，连接矩阵会快速膨胀。 |
| **颜色与状态分散在两处** | 开关与门各自 `match` 颜色字符串，新增颜色要改多处，易不一致。 |
| **新机关类型重复劳动** | 每个新机关（升降台、激光、桥等）都要各自连信号或复制过滤逻辑。 |

整体上：**「谁连谁」在场景里硬编码**，而不是**「发布到某颜色通道，谁订阅谁响应」**的全局模型。

---

## 3. 设计目标（后续你要的能力）

1. **颜色 = 逻辑通道**：开关只声明自己属于哪个颜色通道；机关只声明自己监听哪个通道；**同通道**才响应（与现在字符串比较一致，但连接方式要解耦场景图）。
2. **对全局友好**：尽量少改 `.tscn` 连线；新增机关类型时只实现「订阅 + 应用状态」即可。
3. **可扩展**：多个机关、多个开关（同通道或不同规则）有明确扩展点（见下文「多开关策略」）。

---

## 4. 推荐架构：通道总线（Switch / Mechanism Bus）

核心思想：**开关不直接 `emit` 到具体门节点**，而是向**全局总线**发布「某颜色通道当前应为开还是关」；所有机关在 `_ready` 时向总线注册或连接信号，自行过滤自己的通道。

### 4.1 新增 Autoload（单例）

例如命名：`SwitchChannelBus`（或 `MechanismLinkBus`）。

职责建议：

- 提供信号，例如：  
  `channel_state_changed(channel_id: StringName, is_active: bool)`  
  或保留与现有一致的 `state_label: String`（`"开"`/`"关"`），但**更推荐 bool + 枚举**，在总线边界做一次转换，减少全项目字符串比较。
- 提供方法，例如：  
  `publish_channel_state(channel_id: StringName, is_active: bool)`  
  由**开关**在状态确定改变后调用（动画结束后与现在发信号时机一致即可）。
- （可选）`get_last_state(channel_id) -> bool`：机关 `_ready` 晚于开关时，可同步一次初始状态，避免顺序问题。

这样：**任意关卡**里的开关只需调用 `SwitchChannelBus.publish(...)`，**不依赖** NodePath 是否指向某扇门。

### 4.2 通道 ID：与「颜色」一一对应

- **推荐**：使用 `StringName` 或项目内**单一枚举**（如 `enum SwitchChannel { RED, GREEN, ... }`），总线用 `StringName` 传输（`&"red"` 或 `&"红"`），全项目只在一处维护「显示用中文 / 编辑器中文」与通道 ID 的映射。
- **兼容现状**：可保留导出 `initial_color` 为中文，在开关 `_ready` 里 `channel_id = MechanismColors.to_channel_id(initial_color)`，避免立刻改所有关卡数据。

### 4.3 机关侧统一接口（方便你加新类型）

二选一或组合使用：

**方案 A — 小接口脚本 / 基类**

- 定义 `SwitchControlledMechanism`（`Node` 或 `StaticBody2D` 子类），导出：
  - `@export var channel_id: StringName`（或与开关同源的 color key）
- `_ready()`：`SwitchChannelBus.channel_state_changed.connect(_on_bus_state)`，并 `request_sync()` 读当前通道状态。
- `_on_bus_state(ch, active)`：`if ch != channel_id: return`，再执行开门/关激光等。

**方案 B — 组合而非继承**

- 独立脚本 `switch_channel_listener.gd` 作为子节点挂到门上，导出 `channel_id`，内部连总线并 `call` 父节点的 `apply_switch_state(active)`。

新机关（桥、刺、移动平台）只要实现「**收到 bool（或开/关）后怎么动**」，并挂上同一套 `channel_id`，无需在 `.tscn` 里从每个开关拉线。

### 4.4 开关脚本的改动要点

- 在 `_emit_state_change()`（或等价位置）除保留本地 `emit_signal`（便于过渡）外，调用：  
  `SwitchChannelBus.publish_channel_state(channel_id, is_on)`  
- 过渡期内可：**总线 + 原信号同时发**，待所有门迁到总线后再删掉点对面连接。

### 4.5 多开关、同颜色通道时的规则（需你拍板）

在文档里固定一种默认语义，避免策划歧义：

| 策略 | 含义 | 适用 |
|------|------|------|
| **末次写入** | 任意同色开关翻转，总线只反映「最后一次发布」 | 简单、实现快；多个开关会互相覆盖语义，需关卡设计配合。 |
| **同或（OR）** | 任一同色开关为「开」则通道为开，全关才关 | 适合「多个入口都能开门」。 |
| **全与（AND）** | 全部同色开关为开，通道才为开 | 适合「多钥匙门」。 |

总线内部用一个小字典 `last_state_by_channel` 或 `aggregated_state` 实现即可；开关只 `notify_switch_toggled(channel_id)`，由总线根据策略算出最终 `is_active` 再 `emit`。

## 5. 与 Godot 生态的其它可选增强

- **Groups**：例如 `add_to_group("switch_channel:red")` 仅作调试或批量查找，**不建议**单独用组替代总线（难以表达「状态变化事件」）。
- **Resource**：定义 `SwitchChannelConfig` 资源，在开关和门上引用**同一资源实例**，可在检查器里一眼看出「绑在同一通道」；总线仍负责事件分发，资源只承载 `channel_id` 与显示色。
- **存档**：若机关状态需持久化，在 `to_dict`/`from_dict` 里存「通道最终状态」或「每个机关状态」；总线在场景 `from_dict` 后 `replay_all_channels()` 一次即可。

---

## 6. 从现状迁移的推荐顺序

1. 增加 `SwitchChannelBus` Autoload，实现 `publish` + `channel_state_changed` +（可选）`get_last_state`。
2. 抽出**颜色字符串 → channel_id** 的单一工具（如 `MechanismColors.gd`），开关与门共用，删掉重复 `match`。
3. 修改 `开关.gd`：在发信号同时 `publish` 到总线。
4. 修改 `门.gd`：在 `_ready` 连接总线，用 `channel_id` 过滤；**逐步移除**对 `_on_开关_switch_state_changed` 的编辑器依赖（可保留同名方法转调总线逻辑一段时间）。
5. 清理 `world.tscn`（及其它关卡）里 `switch_state_changed` 的**多条 connection**，改为零连接或仅保留未迁移对象。

---

## 7. 小结

- **现状**：开关通过信号把 `(颜色, 开/关)` 发给场景里**手动连接**的门；颜色过滤在门内完成，但**连接图在关卡里硬编码**，扩展多机关、多开关成本高。
- **推荐**：**颜色 = 通道 ID**，用 **Autoload 总线** 发布/订阅通道状态；机关统一「通道 ID + 应用状态」；多开关用总线内**聚合策略**明确语义。
- 这样后续加「与开关同色联动的任意机关」，主要工作是：**实现机关表现 + 导出 channel_id + 连总线**，而不是在每张地图里拉信号网。

如需把该设计落实为具体 `gd` 文件与 `project.godot` Autoload 条目，可在实现阶段按第 6 节顺序改代码并逐步删旧连接。
